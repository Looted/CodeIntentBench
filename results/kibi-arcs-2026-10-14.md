# Kibi repository arcs, 14 October 2026

The second arc run of CodeIntentBench, on Kibi's own repository: 16 arcs (two per family) about decisions that Kibi's knowledge base already records, seven arms, one attempt each, 112 arc runs and 196 graded sessions. The kibi arm runs on the knowledge base as shipped by Kibi's authors (259 requirements, 33 ADRs, 1,219 facts, 291 test entities, built over months); every other arm receives the same requirements and ADRs rendered into its own container by `projects/kibi/arm-prepare.sh`. Agent: Claude Code with claude-sonnet-5-5 at low effort, 60 turns, $2 and 20 minutes per session. Judge: claude-sonnet-5-5. Total agent cost $87, judge $10. Raw tables: [report-arcs.md](kibi-arcs-2026-10-14/report-arcs.md), [report-arcs.json](kibi-arcs-2026-10-14/report-arcs.json). The project and its arcs are described in [projects/kibi/README.md](../projects/kibi/README.md).

This run answers the objection to the [Papra pilot](papra-arcs-2026-10-14.md): there the kibi arm started from an empty knowledge base and recorded nothing, so the arcs measured capture, not use. Here capture is a given. The question is what a mature knowledge base, with hooks, search and impact checks on top of it, adds over the same knowledge rendered as files, tickets or memories.

One attempt per cell, so every rate carries a wide interval (95% Wilson). Read the ordering and the mechanisms, not the decimals.

## What happened

**A populated knowledge base closes the gap to the file-based arms, but does not open one.** With the same knowledge in every container, the kibi arm went from 31% in the Papra pilot to 50% here, and kibi-conv from 69% to 69%. The ordering among the stores is the same as in the pilot: the arms that put the decision in front of the agent (AGENTS.md in context, a tracker it is told to search, a docs folder it is told to read) pass more arcs than the arms that make the agent find it. Kibi's hooks put the decision in front of the agent too, in every session, and its agents surfaced the recorded decision at 70 to 75% of probes, as often as docs and tracker and more often than agents-md. The difference is in what happened next.

**The kibi arm's failures are of one kind: the agent names the requirement and changes the code anyway.** Six of the kibi arm's ten failed sessions and three of kibi-conv's six are N (surfaced but broke): the hook snippet or `kb_check` told the agent that `REQ-cursor-stop-job-vs-plan`, `REQ-mcp-oneof-guard-input-validation`, `REQ-prolog-bundled-runtime`, `REQ-bootstrap-claim-name-length-v2` or `REQ-engine-daemon-package-versions` governs the code, the agent made the requested change, and its final answer reported that "the KB now contradicts the code" or that the requirement is "stale" and "needs a KB follow-up". In the same situations the tracker and docs agents stopped and asked (S) or rewrote the record and said so (D), which the benchmark accepts. The agent treated the knowledge base as documentation to be updated after the fact, not as a decision to be questioned before the edit. Kibi's own usage skill says why: an unlabelled requirement has firmness `default`, and the skill tells the agent to "follow it unless the task gives evidence against it; then supersede it in the same change … without asking first". One of the repository's 259 requirements carries a `firmness` field at the base commit, so to the plugin every rule in this run, including the two standing arcs' human rules, was an agent's choice that the user's request outranks.

**`kb_check` reported no violations on those edits.** The impact check Kibi's hooks ask the agent to run after editing found "0 violations" in every failed kibi and kibi-conv session, and 12 of the 16 final answers say so, while the same check flagged the requirement as needing "semantic review" or its symbol as "implementing many requirements". Kibi's deterministic checks are about structure (links, coverage, naming); whether the code still does what the requirement says is left to the agent, and the agent read "no violations" as permission.

**Drift: the agent updated the requirement, and search kept showing the old text.** In the swipl drift arc both kibi arms' session-one agents did what Kibi asks: they raised the floor in code and upserted `REQ-prolog-bundled-runtime` with the new statement ("older than version 10.0"). The upsert rewrote the front matter (`semantic_text` and the claim) but left the requirement's Markdown body unchanged, and `kb_search` takes its snippet from the body. Two sessions later, asked to accept 9.x again, the kibi-conv agent searched, read "Kibi must reject a swipl on PATH older than version 9.0" in the result, concluded that the code now matches the recorded decision and that "nothing in the knowledge base needs to change", and reverted the user's decision (V). The kibi agent did the same without searching. Reproduced on a clean checkout with the pinned CLI: after the upsert the file holds both sentences, the search snippet shows the old one, and `kibi sync` reports no changes.

**The convention sentence still matters, less than in the pilot.** kibi-conv adds one sentence telling the agent that decisions live in the knowledge base and to search it before changing behaviour. Its agents looked the decision up before editing in 14 of 25 sessions (kibi: 1 of 28) and passed both surfacing arcs and both branch arcs where the kibi arm passed none and one. The cost is the same as the kibi arm's. In the pilot the sentence was the difference between recording and not recording; here it is the difference between asking `kb_search` and waiting for a hook.

**Standing failed everywhere, again.** Both standing arcs end with a request to drop a firm project rule (foreign Git hooks are never edited; a daemon never serves other package versions) that the knowledge base records as a requirement with its reason. Every arm implemented the request: agents-md, docs, memory and tracker rewrote the record and said so (D, eight of eight), kibi rewrote it once and left it stale once, kibi-conv left it stale twice (N), none removed the rule silently once and named it once. The benchmark accepts only S here, a question back to the user. No agent asked. Kibi's firmness field is the mechanism built for this case, and it was unset on the rules in question, so the hooks had nothing to say beyond "this symbol implements REQ-…" and the skill's `default` rule applied.

That bar is a judgment call: a request from the user is also a reason to supersede, and Kibi's own semantics say so for any decision that is not firm. Under the looser reading, where rewriting the record and saying so (D) also passes a standing probe, arc pass becomes agents-md 94%, tracker 88%, docs 81%, memory 69%, kibi-conv 69%, kibi 50%, none 38%. The file-based arms gain two arcs each because their agents updated the record when they overruled it; the Kibi arms gain nothing because theirs changed the code and left the requirement stale. Both readings are reported here; the strict one is the headline because the family was designed to test it.

**Rationale, navigation and evidence are answered from code.** All seven arms passed both rationale arcs, both navigation arcs and both evidence arcs (the none arm too). The reasons for the 12-word floor and stat-based freshness are in doc comments and ADR text that the code links to; the probes name the behaviour. These families separate arms only when the reason or the location is not recoverable from the repository, which in Kibi's own, heavily commented code it always was.

**agents-md is the most expensive arm by far.** Its container holds the 288 requirements and ADRs as a digest in AGENTS.md, so every session starts with it in context: $1.92 per arc against $0.41 to $0.81 for the others, and no lookups (2 of 25). It still passed the most arcs. The kibi arms spend their extra cost on hook output and `kb_check` calls (121 to 135 s per session against 54 to 78 s).

## Kibi issues found

1. **Release 2.25.0 fails every check.** kibi-cli 2.25.0, kibi-mcp 3.13.0 and kibi-runtime 2.16.1 (npm, 14 October 10:48Z) request a check rule, `decision-firm-edited`, that the published kibi-core 0.22.1 does not know, so `kibi check` and `kb_check` exit with "Unknown check rules requested" on any knowledge base. The commit that added the rule changed kibi-core's Prolog registry but its changeset did not bump kibi-core. Found because kibi-mcp declares kibi-runtime with a caret range and pulled the new runtime into this benchmark's pinned 2.23.0 installation; 31 runs were discarded and re-run with the runtime pinned (`arms/kibi/versions.env`). Fixed the same day: kibi-core 0.22.2 with kibi-cli 2.26.1 and kibi-mcp 3.14.1 install one core and pass `kibi check`.
2. **`kb_upsert` leaves the requirement body stale, and `kb_search` quotes the body.** Upserting a requirement with a new `semantic_text` rewrites the front matter and claims but not the Markdown statement below it; the search snippet comes from the statement, so after a recorded change the search result still shows the old decision, and `kibi sync` sees nothing to do. This turned a correctly recorded decision change into a silent violation two sessions later.
3. **No pre-edit stop on a contradicting change.** The hooks name the governing requirement before an edit, but neither they nor `kb_check` compare the change against the requirement's statement; "0 violations" after a change that contradicts the requirement is the normal result. The one place Kibi could have stopped the agent is also the one place it did not.
4. **Firmness is not set on the shipped knowledge base.** Schema 10 carries `firmness: firm` with an origin reference and the plugin's skill treats an unlabelled decision as `default`, to be superseded without asking. One of 259 requirements at the base commit sets `firmness`; the rules the standing arcs defend do not. Kibi's own knowledge base has not adopted the mechanism Kibi ships.
5. **`kb_upsert` still rejects first attempts.** Ten upsert calls in three sessions failed on schema details (`semantic_inventory_version`, unknown `text`/`body` properties, `proof_receipts` append-only, relationship source mismatch); each cost a `kb_model` round trip.

## Benchmark notes and caveats

- **One attempt per cell.** The ordering agents-md ≈ tracker > docs ≈ kibi-conv > memory > kibi > none is consistent with the Papra pilot; individual cells are not stable.
- **A control step with an exact-text test.** The second session of `kibi-swipl-minimum-drift` asks the agent to add the searched directories to the swipl-not-found error. A repository test asserts the exact error text, so agents that reworded the message failed the step (F) in agents-md, kibi and kibi-conv. For kibi and kibi-conv the arc fails on session three regardless; for agents-md this is the only failed session, so its arc pass is 81% as graded and 88% with that step treated as passed. The step's regression suite should exclude that test.
- **Judge change and re-judge.** The judge's "invented constraint" question did not know the one-sentence convention the convention arms are given, and graded a tracker agent's "per the project rules, a new decision goes into the tracker" as an invented constraint (I). The prompt now carries the arm's convention; re-judging the 80 non-kibi runs with it changed 3 of 140 outcomes (that I became C; one N became V and one S became Q, judge sampling noise).
- **Regression failures on probe steps are expected.** When a probe asks for the opposite of a recorded decision and the agent complies, the repository's own tests for that decision fail; the decision table ignores the regression result for D, N and V outcomes, so those failures do not change the grade.
- **The benchmark container runs as root.** Eight chmod-based tests fail on an untouched checkout and are recorded without being counted (`tests.ignore`).
- **Base commit.** All arcs run on `develop` at 9f3311f3 (knowledge-base schema 10), the schema the pinned 2.23.0 release reads. Kibi's own Claude Code wiring (`.claude/settings.json`, `.mcp.json`) is removed from every arm's workspace so the pinned plugin and CLI are the only Kibi the agent gets.
